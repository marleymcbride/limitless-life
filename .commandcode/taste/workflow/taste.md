# workflow
- The user tracks work as explicit task lists and expects each item confirmed as done or still-open when asked. Confidence: 0.6
- Before re-confirming or re-delegating a previously written integration plan/handoff to an external developer, verify the actual current state of the code (endpoints, auth, event tracking) — don't assume the old handoff doc is still accurate. External devs may have implemented integrations independently without an explicit handoff, so the live code is the only source of truth. Confidence: 0.75
- When the user asks whether an integration is working as intended ("is it all working the way we want it?"), give a candid, evidence-based audit: confirm what's solid, but surface real bugs and metric gaps found in the code (e.g., score mismatches, leads missing from dash metrics), then propose small low-risk fixes and ask before implementing. Confidence: 0.6
- Don't run `git stash` (or similar commands that temporarily modify the working tree) without first explaining what it does and getting explicit approval — the user will deny it. Prefer non-destructive verification (e.g., `npx tsc --noEmit`) over stash/pop to prove pre-existing test failures. Confidence: 0.7
- For verifying a small edit is safe, prefers quick targeted checks (e.g., single-file `eslint`/typecheck) over full builds or full typechecks — will approve a check only if it's quick ("ok if its a quick test"). Confidence: 0.6
- When reporting problems, explicitly separate pre-existing test/environment failures (e.g., broken jest config, wrong worktree node_modules) from actual product breakage — the user cares about whether the feature works at runtime and will push back ("works fine though?") if test-file noise is framed as if the feature is broken. Confidence: 0.6
- For site/offer state (e.g., whether a cohort or offer doc is open), prefers a simple on/off toggle the user can flip themselves (e.g., an admin-dashboard switch backed by the DB) rather than build-time constants or code edits — they want to be able to say "re-open the offer doc" and have it go live again without a deploy, and they'll ask to try the switch themselves rather than have the agent flip it for them. Confidence: 0.8
- When the user has manually set an offer/cohort flag themselves (e.g., "i have turned it off — i want it off"), treat their state as authoritative: don't flip it back to live because the DB looks inconsistent with an earlier session — the user manages these flags directly and their current state is final unless they ask to change it. Confidence: 0.8
- When an offer/cohort is closed, prefers replacing the application/deposit CTA with a waitlist-details collection (keep capturing leads) rather than removing the conversion path entirely — and actively shapes the mechanism (e.g., an inline waitlist form) rather than leaving the decision to the agent. Confidence: 0.75
- When an offer doc is in its closed/off state, keep it free of leftover sales copy from the live state (e.g., "skip the sales call" pitches, personal sign-offs like "You in? — Marley") — the closed page should show only the closure message and the waitlist form; sales-y lines belong only in the live state. Confidence: 0.65
- When a feature depends on external services (Fillout forms, n8n workflows, external backends), first verify in code whether those pieces actually exist and feed the internal DB, then split the plan explicitly into what the agent will build internally vs. what the user must go build/configure externally — the user wants to be handed their own task list ("think in the lens of what you want/need me to go build"), not assumptions that external infrastructure is ready. Confidence: 0.8
- When the agent recommends an approach that deviates from the user's existing tooling (e.g., an inline form over the Fillout forms already in the project), the user asks "why" and expects the rationale backed by concrete code evidence (e.g., the existing Fillout path hits stubbed code and never lands in Leads), not just the recommendation — justify deviations from existing infrastructure explicitly. Confidence: 0.6
- For a state-gated feature that isn't deployed yet (e.g., the programme-live toggle), prefers to test the behaviour by having the agent manually flip the DB flag first ("try a manual flip first, to test it") to verify the gating logic works before any deploy — a direct DB flip is an acceptable, desired pre-deploy verification step. The user asks the agent to perform the flip for each new flag/feature as it's added ("now try a manual flip for Limitless Concierge"), and typically verifies visually right after the flip. Confidence: 0.8
- Manually toggling offer/cohort state is a routine, delegated operation: when the user says "manual toggle the cohort back on" / "manual trigger the cohort back open", they expect the agent to flip the DB flag directly (e.g., a psql `UPDATE app_settings SET value = 'true' WHERE key = 'programme_live'`), not to edit code or deploy — direct DB flips are the accepted way to open/close an offer on demand. Confidence: 0.75

# workflow
- The user tracks work as explicit task lists and expects each item confirmed as done or still-open when asked. Confidence: 0.6
- Before re-confirming or re-delegating a previously written integration plan/handoff to an external developer, verify the actual current state of the code (endpoints, auth, event tracking) — don't assume the old handoff doc is still accurate. External devs may have implemented integrations independently without an explicit handoff, so the live code is the only source of truth. Confidence: 0.8
- When an external specialist challenges the correctness of a claim in a handoff doc (e.g., "did you really multiply by an FX rate or just relabel GBP pence as USD cents?"), answer by reading the live code and giving exact, quotable proof — file paths, line numbers, and a worked example with real numbers (£197 → 25019 USD cents) — rather than restating the doc; the user forwards this answer to the specialist verbatim, so it must be definitive and evidence-backed. Confidence: 0.6
- When an external specialist replies with a direct factual question (e.g., "what's the exact database name in the connection string?"), answer by extracting the exact value from the live config (.env.local `DATABASE_URL`) and hand the user a short, paste-ready reply — the value itself plus just enough parsed context (host/port shape) for the specialist to confirm they're looking at the right resource. Confidence: 0.6
- When the user asks whether an integration is working as intended ("is it all working the way we want it?"), give a candid, evidence-based audit: confirm what's solid, but surface real bugs and metric gaps found in the code (e.g., score mismatches, leads missing from dash metrics), then propose small low-risk fixes and ask before implementing. Confidence: 0.6
- Don't run `git stash` (or similar commands that temporarily modify the working tree) without first explaining what it does and getting explicit approval — the user will deny it. Prefer non-destructive verification (e.g., `npx tsc --noEmit`) over stash/pop to prove pre-existing test failures. Confidence: 0.7
- For verifying a small edit is safe, prefers quick targeted checks (e.g., single-file `eslint`/typecheck) over full builds or full typechecks — will approve a check only if it's quick ("ok if its a quick test"). Confidence: 0.6
- When reporting problems, explicitly separate pre-existing test/environment failures (e.g., broken jest config, wrong worktree node_modules) from actual product breakage — the user cares about whether the feature works at runtime and will push back ("works fine though?") if test-file noise is framed as if the feature is broken. Confidence: 0.6
- For site/offer state (e.g., whether a cohort or offer doc is open), prefers a simple on/off toggle the user can flip themselves (e.g., an admin-dashboard switch backed by the DB) rather than build-time constants or code edits — they want to be able to say "re-open the offer doc" and have it go live again without a deploy, and they'll ask to try the switch themselves rather than have the agent flip it for them. Confidence: 0.85
- Expects a DB-backed state toggle to take effect on the live site immediately, without a new commit/deploy — if the deployed page still shows stale state because it's statically pre-rendered and baked at build time, the user treats that as a flaw in how the trigger was set up ("is that how you set it up?") and expects the gated pages to read state fresh per request (e.g., force dynamic rendering). Explicitly approved adding `export const dynamic = 'force-dynamic'` to all gated offer pages, accepting the slower page-load tradeoff since it makes the toggle work reliably without commits. The same stale-cache bug also surfaced on the admin dashboard's programme-open toggle lights (lights reset to green on refresh even after the user flipped them off, while the DB correctly had `false`), and the same `force-dynamic` fix was applied to the admin `programme-state` API route — state-backed admin API routes and public gated pages alike must never serve a cached first response, so the UI always reflects the real DB value on load. Confidence: 0.9
- When the user has manually set an offer/cohort flag themselves (e.g., "i have turned it off — i want it off"), treat their state as authoritative: don't flip it back to live because the DB looks inconsistent with an earlier session — the user manages these flags directly and their current state is final unless they ask to change it. Confidence: 0.8
- When an offer/cohort is closed, prefers replacing the application/deposit CTA with a waitlist-details collection (keep capturing leads) rather than removing the conversion path entirely — and actively shapes the mechanism (e.g., an inline waitlist form) rather than leaving the decision to the agent. Confidence: 0.75
- When an offer doc is in its closed/off state, keep it free of leftover sales copy from the live state (e.g., "skip the sales call" pitches, personal sign-offs like "You in? — Marley") — the closed page should show only the closure message and the waitlist form; sales-y lines belong only in the live state. Confidence: 0.65
- When a feature depends on external services (Fillout forms, n8n workflows, external backends), first verify in code whether those pieces actually exist and feed the internal DB, then split the plan explicitly into what the agent will build internally vs. what the user must go build/configure externally — the user wants to be handed their own task list ("think in the lens of what you want/need me to go build"), not assumptions that external infrastructure is ready. Confidence: 0.8
- When the agent recommends an approach that deviates from the user's existing tooling (e.g., an inline form over the Fillout forms already in the project), the user asks "why" and expects the rationale backed by concrete code evidence (e.g., the existing Fillout path hits stubbed code and never lands in Leads), not just the recommendation — justify deviations from existing infrastructure explicitly. Confidence: 0.6
- For a state-gated feature that isn't deployed yet (e.g., the programme-live toggle), prefers to test the behaviour by having the agent manually flip the DB flag first ("try a manual flip first, to test it") to verify the gating logic works before any deploy — a direct DB flip is an acceptable, desired pre-deploy verification step. The user asks the agent to perform the flip for each new flag/feature as it's added ("now try a manual flip for Limitless Concierge"), and typically verifies visually right after the flip. Confidence: 0.8
- Manually toggling offer/cohort state is a routine, delegated operation: when the user says "manual toggle the cohort back on" / "manual trigger the cohort back open", they expect the agent to flip the DB flag directly (e.g., a psql `UPDATE app_settings SET value = 'true' WHERE key = 'programme_live'`), not to edit code or deploy — direct DB flips are the accepted way to open/close an offer on demand. Confidence: 0.75
- When a manual flag flip doesn't show up on the page ("it still shows as closed?"), the user expects a root-cause diagnosis — verify the DB value AND whether the app/dev server is actually running so the change can be picked up — rather than just re-flipping the flag or assuming the flip took effect. Confidence: 0.6
- When given a choice between a code/integration change and manually updating an external data source (e.g., updating Airtable campaign revenue to USD), prefers the simplest manual fix — will go update the external data themselves ("i can go update the Airtable") to match the canonical internal format and keep all dashboard surfaces consistent, rather than having the agent wire the external source to the DB. Confidence: 0.65
- Before prescribing a manual data-fix step for an external store (e.g., "update Airtable campaign revenue to USD"), verify whether that store is actually auto-populated by an integration (e.g., an n8n aggregation overwrites Airtable Campaigns.Revenue every 5 minutes from Postgres) — if the external store self-heals from the canonical DB, the manual cleanup step is unnecessary and should be dropped; confirm the real integration chain rather than assuming the field is hand-maintained. Confidence: 0.7
- When validating an integration/data-integrity claim (e.g., that stored payment values are "genuinely USD cents, not relabeled pence"), confirm it against live database values (e.g., a psql query showing actual rows and totals: £100 → 13440 USD cents, total 241920) in addition to reading the conversion code — the specialist works from "the actual workflow, not assumptions," so proof should be evidence-backed with real numbers from the running system. Confidence: 0.6
- When building a replay/backfill script that pushes DB records to an external webhook (e.g., replaying legacy payments into n8n→Airtable), first verify the webhook's required fields against the actual data (e.g., legacy payments lack `stripePaymentId`, so they'd be rejected) — audit prerequisites before writing the replay, and prefer routing through the same webhook the live app uses so replayed records land identically to live ones. Confidence: 0.6
- A data-parity fix must cover future/ongoing entries, not just historical records — after a one-off replay of existing records is proposed, the user follows up ("what about next/new manual entries?") expecting a durable entry point (e.g., an admin "record manual payment" form/API that writes Postgres AND fires the same n8n→Airtable sync), not a script that only patches the past. The recurring case is explicit: legacy off-Stripe clients "are still coming in each month," so the mechanism must be repeatable month after month. Confidence: 0.75
- For recurring manual data entry (e.g., off-Stripe/legacy client payments that come in monthly), prefers a simple self-service admin UI form they can use ad-hoc (email + £ amount + tier, recorded as USD) rather than one-off scripts or agent-run DB inserts — the user wants to "just add them" themselves as payments arrive. Confidence: 0.65
- The user verifies whether a fix works on the deployed production site, not localhost — a change that exists only in the local working tree (uncommitted/un-deployed) is still "broken" from their view ("it's still showing cohort is 'on' / green"). When diagnosing a persisting stale-state report, check deploy/git state (git log/diff to see if the fix is committed, curl the production URL for cache headers like `x-vercel-cache`, confirm no dev server is running) to distinguish "cached at build" from "fix not deployed yet," and offer to commit the pending work so it can actually ship. The user will push back on a "not deployed yet" diagnosis with their own behavioral evidence (e.g., "nah the force-dynamic is deployed, the live offer docs change now without deploys") — take that as ground truth, but remember deployments can be partial: one feature's code being live (offer docs) doesn't mean another feature's build is (admin dashboard), so verify the specific feature by inspecting the deployed production JS chunks for its markers (e.g., grep for feature strings like `programme-state`/`record-payment`) before concluding. Confidence: 0.7
- When an admin dashboard metric reads zero/stale mid-period (e.g., "MARKETING THIS MONTH — YT views 0" on the 10th of the month), diagnose by checking the DB table's most recent rows first, then whether any code in the repo writes to that table — if nothing in the codebase writes it, the table is fed externally (n8n), so the gap is an upstream ingestion stop (e.g., feed silent since a prior date), not an app code bug; present the evidence (last populated date, row counts) rather than treating the zero as a defect. The user expects dashboards to reflect current data and flags stale zeros as something to investigate. Confidence: 0.6
- The user scrutinizes admin-dashboard metric values that look implausible — not just zeros but also unexpected/wrong-looking figures (e.g., "why does my admin dash show 'YT VIEWS 2,861'?? that can't be right") — and expects the agent to investigate how that metric is actually computed (read the stats route) and verify the underlying data rather than accept the displayed number at face value. The user treats an independent external platform's ground-truth (e.g., their own YouTube Studio channel analytics — "3,051 views in the last 28 days... checks out") as authoritative to corroborate a contested metric; once the dashboard figure is reconciled against that source and the underlying feed is confirmed flowing again, they accept the number as correct and drop their initial suspicion. Confidence: 0.6
- When the user pastes a dev-only console error/warning (e.g., a Next.js react-hydration-error) and asks "is this a problem?", they want a clear yes/no verdict with a concrete diagnosis — identify the actual root cause (e.g., a browser-extension-injected attribute like `inject_newsvd="true"` on the `<body>`) and state plainly that it's not a code bug and is dev-only, rather than lumping it in with real breakage. The user distinguishes noise from actual product problems. Confidence: 0.6
- There are multiple near-identical offer-doc variants in the repo (e.g., `intake-open-doc-beta`, `intake-open-doc-beta-waitlist`, and variants for other offers) — when asked to edit an offer doc, the user wants the REAL/live production version, explicitly NOT a "beta" or "waitlist" placeholder variant ("we want to be in the real one. not waitlist. not beta."). Verify which doc is the actual live cohort offer (own pricing/CTA sections, non-waitlist) before editing, rather than defaulting to the first matching path. Confidence: 0.6
- Distinguishes the site's page hierarchy by purpose: the "main sales page" (e.g., "the main LC home sales page") is the evergreen VSL page at `/`, NOT the offer-doc page (e.g., `/limitless-concierge-invitation` — "that's OBVOISULY not the sales page? that's the offer doc page"). When asked to put a CTA/button on "the sales page," confirm the route is actually the sales/VSL page before editing; confusing the offer doc with the sales page is treated as an obvious, avoidable error. Confidence: 0.6
- The user iterates on copy and UI text with rapid-fire, often-reversed instructions ("instead do…", "nah, keep the…", "in fact, have '[CLOSED]' as an eyebrow") — apply the most recent instruction verbatim to the existing element; their latest message supersedes earlier decisions, and superseded versions should not be preserved, re-introduced, or "improved" on. Confidence: 0.65

When the task is straightforward and the agent already knows the structure, don't do full reads of every section before each edit — make the targeted edits directly and verify once at the end, rather than re-reading the file to "be safe" before every single change. Confidence: 0.7

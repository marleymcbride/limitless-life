# workflow
- The user tracks work as explicit task lists and expects each item confirmed as done or still-open when asked. Confidence: 0.6
- Before re-confirming or re-delegating a previously written integration plan/handoff to an external developer, verify the actual current state of the code (endpoints, auth, event tracking) — don't assume the old handoff doc is still accurate. External devs may have implemented integrations independently without an explicit handoff, so the live code is the only source of truth. Confidence: 0.75
- When the user asks whether an integration is working as intended ("is it all working the way we want it?"), give a candid, evidence-based audit: confirm what's solid, but surface real bugs and metric gaps found in the code (e.g., score mismatches, leads missing from dash metrics), then propose small low-risk fixes and ask before implementing. Confidence: 0.6
- Don't run `git stash` (or similar commands that temporarily modify the working tree) without first explaining what it does and getting explicit approval — the user will deny it. Prefer non-destructive verification (e.g., `npx tsc --noEmit`) over stash/pop to prove pre-existing test failures. Confidence: 0.7
- For verifying a small edit is safe, prefers quick targeted checks (e.g., single-file `eslint`/typecheck) over full builds or full typechecks — will approve a check only if it's quick ("ok if its a quick test"). Confidence: 0.6
- When reporting problems, explicitly separate pre-existing test/environment failures (e.g., broken jest config, wrong worktree node_modules) from actual product breakage — the user cares about whether the feature works at runtime and will push back ("works fine though?") if test-file noise is framed as if the feature is broken. Confidence: 0.6
